One starting checkpoint, two trained arms, one sealed test set. 1. Three arms, two contrasts

Everything starts from the same pinned Qwen3-8B revision. The defence arm trains on AuditBench investigation tasks. The control arm uses the identical recipe on non-security terminal tasks, so that generic "learning to use a terminal" is separated from learning to investigate logs. Each trained arm exports a dev-selected checkpoint (S) and its terminal checkpoint (T). Stage 2, which is out of scope here, evaluates all of them before and after.

2. Data: files become provenance groups, groups become splits

AuditBench ships 129 log files from two sources: Lab (Linux and Windows audit logs, edge and raw views) and OpTC (edge view). Many files are copies, re-views or windows of the same attack run, so files are not independent. The split is therefore done on provenance groups: files linked by identical content, a shared scenario key, the same host on the same day, or a window overlap are one group, and a group goes to exactly one split.

3. What one task looks like

The agent never sees the log in its prompt. It gets a terminal in a sandbox with the log as a read-only file, searches it with rg, jq and Python, and writes its findings as a JSON file. Grading happens in a second container that receives only that file. Model calls go to a vLLM server outside the sandbox.

4. Reward: binary, strict, evidence-grounded

A trajectory earns 1 only when it reports every supported target and nothing else at high confidence. Partial detection and tolerated false alerts are both scored 0, so the policy cannot climb by over-reporting or by learning the grader's leniency. The original benchmark's counting is kept as a separate compatibility metric and never used as reward.

Pilot-only contingency. If fewer than 10% of at least 50 sampled positive train prompt-groups show any reward variance, one predefined dense alternative may be compared in the pilot: R = (TP/|G|) / (1 + FP) for positive investigation, binary elsewhere. One recipe is then frozen and the main run restarts from original weights. Rewards are never changed mid-run.

5. The training loop

Online GRPO with fresh rollouts every iteration. Step 1 baseline trajectories are diagnostic data only, never a replay buffer. A balanced sampler decides which tasks are drawn: task type uniformly, then positive versus negative with probability one half, then a provenance group uniformly, so long files and repeated benign views cannot dominate by count.

Pilot first (≤ 10 iterations)

Before the main run, one pilot must show: pinned configs accept every field, loss masks cover only assistant tokens, sampler and trainer logprobs agree on identical prefixes, synthetic groups give the expected advantage signs, a resume and an export reload reproduce the live policy, and resource peaks fit. It also measures time per iteration, which sets the iteration cap under the budget.

Pilot weights, optimiser and RNG are discarded. The main run starts again from original weights in a new directory.

6. Picking a checkpoint and stopping

Training reward cannot answer the manipulation check, because a policy that learns to report nothing scores well on negative tasks. Selection therefore uses a balanced dev score that rewards false-positive-free recall on positive groups and clean output on negative groups, with false-alert and validity constraints relative to step 0.

P_t = mean per positive group of false-positive-free target recall (classification: sensitivity) N_t = mean per negative group of valid clean-output rate (classification: specificity) D = mean over the four tasks of (P_t + N_t) / 2 eligible(step) ⇔ F ≤ F_base + 0.02 and V ≥ V_base − 0.01 F = negative-task high-confidence alert rate, V = output validity S = argmax D over eligible steps, ties to the earlier step, step 0 included manipulation check passed ⇔ D_S − D_0 ≥ 0.10 with improved positive recall

7. Where things run

A laptop drives everything through SkyPilot. The GPU node holds the policy server and the trainer. Sandboxes live on Modal because RunPod pods cannot run nested containers. State that must survive the pod lives on a network volume. Every phase runs under a spend guard and stops the pod when it finishes, because idle pod time was the dominant leak.

8. Budget: a hard $1,500 cap

The cap replaces the open-ended plan. After the pilot, the main-run iteration count is T_max = min(100, floor(per-arm budget / measured cost per iteration)), and control trains to the defence terminal step within its own share.

What the 2026-10-07 smoke run said. All 445 train and dev tasks ran once on the real Qwen3-8B path through Modal. Mean strict reward was 0.571, almost entirely from negative tasks: positives were detected in 1 of 27, and classification produced a valid answer in 1 of 15. A third of trials gave invalid output, mostly because the agent concluded "benign" and ended without writing findings.json; a tenth ran out of context. The instruction template now carries an explicit required-output paragraph, so the baseline and all arms use amended tasks and the smoke trajectories are not comparable to them. Whether positive-task reward variance is sufficient for GRPO is exactly what the baseline and pilot gates test.

10. What this design can and cannot claim

  • Experimental unit is the provenance group, not the window or the attempt. Paired bootstrap intervals resample groups with all their views and attempts together. With 18 train and 7 dev groups, precision is limited.
  • One seed per arm is exploratory. Intervals are conditional on that run; they do not estimate training-seed variation.
  • The control matches declared budgets, not compute. Actual updates, tokens, rollouts and time are logged for both arms; equal iterations is the convention.
  • A null offence difference is not evidence of no uplift without adequate precision and a predeclared equivalence margin, which Stage 2 sets before results are opened.
  • AuditBench-Agent is an adaptation. Whole-file classification and terminal-mediated log access differ from the paper's protocol; its scores are not paper-reproduction scores.
  • Labels are closed-world. A window without an annotated target is not proof of benign activity. Unmatched findings count as false positives regardless.
  • Host-held-out and template-held-out generalisation are not established by this split; Lab Linux scenarios share one host.

Pilot outcomes that must be written into PREREG.md before it freezes: the reward-variance rule outcome, 32k versus 64k context, the realised observation cap in tokens, the logprob consistency tolerance, resource peaks, failure rates, and the rollout, GPU-hour and dollar caps.
